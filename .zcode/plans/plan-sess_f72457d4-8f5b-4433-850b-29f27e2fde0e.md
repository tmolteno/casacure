# Implement casacore's locking protocol in casacure

## Goal

Real OS-level table locking, byte- and behavior-compatible with casacore, so a casacure process and a real casacore/python-casacore process arbitrate access to the same table through `<dir>/table.lock` fcntl record locks. This replaces today's advisory `lock()`/`unlock()` flag and closes the "one writer per table, but nothing enforces it" gap flagged in issue #11.

Verified protocol facts this builds on (from casacore upstream source cross-checked against the installed `libcasa_tables.so.9` and real lock files `PARENT.tab/table.lock`, `test.ms/table.lock`):

- **fcntl regions** on `table.lock` (seqnr 0): byte 0 len 1 = the read(shared F_RDLCK)/write(exclusive F_WRLCK) lock; byte 1 = "in use" lock (read-locked by every open process; `ismultiused` = try write-lock on byte 1); bytes 1–2 (len 2) when permanent locking is active.
- **acquire semantics**: `nattempts == 0` → blocking `F_SETLKW`; otherwise N × non-blocking `F_SETLK` with `sleep(1)`; `ENOLCK` treated as success (NFS); waiter appends its pid to the 260-byte request list while retrying and removes it after.
- **table.lock layout**: 260-byte request list (`u32` count + ≤32 × (pid, hostId=0) i32), then `u32` infoLeng, then AipsIO stream containing the `sync` object: `[u32 nameLen=4]["sync"][u32 ver=1|2][nrrow u32|u64][nrcolumn i32][modifyCounter u32]` and, when `nrcolumn >= 0` (full form), `[tableChangeCounter u32]` + nested `"Block"` object of per-DM counters. Reader (casacore) prefers sync `nrrow` over `table.dat`; resyncs rows on every fresh acquire; re-opens `table.dat` only if `tableChangeCounter` changed; errors if `nrcolumn` differs.
- **LockOption enum** (numeric order): PermanentLocking=0, PermanentLockingWait=1, AutoLocking=2, UserLocking=3, AutoNoReadLocking=4, UserNoReadLocking=5, NoLocking=6, DefaultLocking=7. Defaults: interval 5 s, maxwait 0 (indefinite). `default` → AutoLocking. Writable open → write locks; readonly → read locks; `autonoread`/`usernoread`/`nolock` disable read locking (fetch sync info without holding a lock).
- **Lifecycle**: `permanent` = acquire at open (1 attempt, throw on failure); `permanentwait` = block; `user` = read lock at open then immediately released, lock only via explicit `lock()`; `auto` = read lock held from open, write lock on first write, released when a waiter appears in the request list (inspect throttled: every 25th call AND ≥interval seconds), re-acquired on next operation. Release writes the sync record (full form) into the lock file at offset 260, then F_UNLCK. Locks are released on close/drop after a final flush.
- **Missing `table.lock`** (e.g. byte-level copies): open with create=False → all lock requests succeed, no actual locking — casacure must match this, not create lock files on open.
- **python-casacore surface**: `table(..., lockoptions='default')` accepts `default, auto, autonoread, user, usernoread, permanent, permanentwait` (str, or dict `{'option': ..., 'interval': 5, 'maxwait': 0}`); `lock(write=True, nattempts=0)`, `unlock()`, `haslock(write=True)`, `lockoptions()`, `ismultiused()`.

## Changes

### 1. New core module `crates/casacure/src/lockfile.rs`

- Add `libc` dependency to `crates/casacure/Cargo.toml` (fcntl F_SETLK/F_SETLKW/F_UNLCK via `struct flock`).
- `FileLocker { fd, start, len }` with `acquire(Read|Write, nattempts)` (blocking when `nattempts==0`, else N tries with 1 s sleep), `probe_write()` (for in-use/multi-used checks), `release()`. `ENOLCK` → success, one-time stderr note, like casacore.
- `LockFile`: open/create `table.lock` keeping the **fd for the handle's lifetime**; `create` flag (true only on table create), `must_exist=false` semantics (missing file → no-locking mode, every request succeeds); `acquire`/`release`/`is_multi_used`; request-list add/remove (`SIZEREQID=260`, BE ints); `inspect(interval)` implementing casacore's 25-call + interval throttle reading the waiter count.
- **Sync record**: full parse of the existing `sync` object (nrrow, nrcolumn, modifyCounter, tableChangeCounter, per-DM Block — reusing `aipsio.rs` framing) and write of the full form (see flush below). All reads/writes via `pread`/`pwrite` on the held fd.

### 2. Lifecycle integration (`crates/casacure/src/table.rs`, `grow.rs`)

- New `LockOptions { option: LockMode, interval: u32, maxwait: u32 }` mirroring the 8 casacore modes with the same defaults/normalizations.
- `Table` gains `lock: Option<LockFile>` (+ `lock_held: LockState`). `Table::open`/`create` take `LockOptions`:
  - create → create `table.lock`, write initial sync record (so casacore can lock against casacure-created tables).
  - open → attach (never create); permanent/permanentwait acquire write (writable) or read (readonly) at open, throw on failure; auto/user acquire read at open when read-locking (user releases immediately); `nolock`/missing file → attach nothing.
  - On fresh read-lock acquire: re-read sync record → update `nrow`; if `tableChangeCounter` changed → re-open `table.dat` + DM files in place (resync); `nrcolumn` mismatch → error (casacore's message).
- `lock(&mut self, write, nattempts)` / `unlock(&mut self)` become real (unlock flushes first when write-locked); `has_lock(write)`.
- `flush` (writable): after writing files, write the **full-form sync record** through `LockFile::putInfo` — nrrow, `nrcolumn = ncols`, `modifyCounter + 1`, tableChangeCounter and DM counters **preserved** (rows changed only; keeps casacore readers on the cheap resync path instead of a full `syncTable`). This supersedes `patch_lock_nrrow`; `patch_lock_nrrow` is retired from the flush path but keeps its missing-file no-op contract for `patch_copy_nrow`-style uses.
- **fcntl close hazard rework**: POSIX drops a process's record locks when *any* fd to the file closes. All `table.lock` access must go through persistent fds: `lock_sync_nrrow` (read path at open) and `patch_lock_nrrow` switch from `std::fs::read/write` to `pread/pwrite` on the handle's fd (or a short-lived dup that is *not* closed while locks are held — simplest correct form: read via the LockFile fd; for transient opens before locking, plain fs::read is still safe because no locks are held yet at that point — the invariant to enforce and document: *no `std::fs` open of `table.lock` while any lock on it is held in-process*).
- Auto-release (AutoLocking): `inspect`-and-release hook invoked from the binding choke points (every Python-visible operation increments the counter; after ≥25 calls or interval seconds, if a waiter is registered → flush + release; next operation re-acquires + resyncs). Implemented as small `ensure_read_lock`/`ensure_write_lock`/`auto_release` helpers so both core callers and the Python layer funnel through them.
- Drop: `Table`/`WritableTable` release the lock on drop (flush-if-writable semantics stay as today; only the fcntl release + sync write is added). Python `close()`/`__exit__` already call flush explicitly.

### 3. Python surface (`crates/casacure-python/src/table.rs`)

- `table(...)` constructor: add explicit `lockoptions='default'` kwarg (str or dict `{'option', 'interval', 'maxwait'}`) with casacore's exact accepted strings and error message (today it is silently swallowed by `**_kwargs`). Thread it through `open_or_create` → core.
- The shared `WriteData` owns the canonical write-side `LockFile` for the directory (consistent with the existing one-buffer-per-dir registry); read snapshots attach their own read locks.
- Methods: `lock(write=True, nattempts=0)`, `unlock()`, `haslock(write=True)`, `lockoptions()`, `ismultiused()`; keep `resync()`/`datachanged()` out of v1 (not needed by surveyed consumers). Blocking waits and retry loops run under `py.detach` so the GIL isn't held.
- Auto-lock/release hooks wired into the public methods via the core helpers; `readonly` Python opens pass the real `lockoptions` through (note: core-level `readonly=false` pass-through today is unchanged — locking keys off the Python-visible mode + options, per the explorer's finding #2).

### 4. Compatibility fixes that fall out

- Full-rewrite flush branch (`create_table` path) now writes the sync record too, fixing the stale-`nrrow`-after-shrink hazard the explorer found (`table.rs:2327-2336` vs `:2425-2426`).
- Stale doc comments updated: `struct Table` "all file contents are owned" (predates mmap), `flush` no-op comment, `lock()` "advisory only" docstrings, CHANGELOG §2 "no OS locks are held" line, TODO §2, ARE_WE_CURED §2 row, DIFFERENCES.md gains a locking entry documenting exactly where casacure's auto-locking release behavior is checked (binding choke points) and the missing-lock-file = no-locking parity.

### 5. Tests

- **Rust unit**: sync-record full parse/write round-trip; format checks against the real casacore lock files already on disk (`PARENT.tab`, copied fixtures into `tests/data/`); LockFile acquire/release/conflict via a child process (`std::process::Command` + `current_exe` test-bin pattern) since fcntl locks don't conflict within one process; missing-lock-file = no-locking; `is_multi_used`.
- **Rust integration**: two casacure processes alternating writes under `user` and `permanentwait`; `permanent` open throws when a writer holds; reader resync (nrow + content) after another process grows the table.
- **Python**: `lockoptions` validation; `lock`/`unlock`/`haslock`/`lockoptions()`/`ismultiused()`; two-subprocess contention test; the existing e2e suite must stay green (same-process double-opens are pervasive — fcntl's per-process semantics make this safe; `flock` is explicitly NOT used, for exactly this reason).
- **Interop acceptance gate (the real test)**: against the real python-casacore 3.8.1 in `/home/tim/.venvs/ccdev`: (a) casacore `permanentwait` writer excludes a casacure writable open and vice versa; (b) casacure writes + flushes, casacore reopens and sees correct `nrrow` and data; (c) casacore writes, casacure `lock()` resyncs and sees the new rows; (d) `ismultiused` agrees with a live casacore handle; (e) dask-ms smoke suite unaffected by the new default locking.
- Bench suite (`scripts/bench_*`) unaffected — no new syscalls on read-only paths without contention.

### 6. Out of scope (recorded in DIFFERENCES.md)

- casacore's bucket-level per-storage-manager data locks (internal to casacore's SSM bucket cache; irrelevant while casacure owns its buffers per process).
- Memory tables, NFS fsync toggles, and the `DefaultLocking`-follows-existing-PlainTable nuance (casacure has one PlainTable-equivalent per directory by construction).
